# Revisiting arrays and pointers with generics

**[You can find all the code for this chapter here](revisiting-arrays-and-pointers-with-generics/)**

In the [arrays chapter](arrays-and-pointers.md) we wrote `struct ints` by hand:
a growable list of `int`s. In the [generics chapter](generics.md) we wrote a
macro that generates that list for any type. Now let's put them together and
write the three functions that make a collection *useful* — `reduce`, `map` and
`filter` — once, in terms of the generic array.

## Start from the macro

Declare an `int_array`:

```c
#include "generic_array.h"

DEFINE_ARRAY(int_array, int)
```

That gives us `struct int_array`, `int_array_init`, `int_array_push` and
`int_array_free`, all type-correct for `int`.

## Write the test first: reduce

`reduce` folds a collection down to a single value. For a sum:

```c
static void test_reduce(void)
{
    const int values[] = {1, 2, 3, 4};
    struct int_array a = make_ints(values, 4);

    CHECK_INT(reduce_sum(&a), 10);

    int_array_free(&a);
}
```

## Write enough code to make it pass

```c
int reduce_sum(const struct int_array *a)
{
    int total = 0;

    for (size_t i = 0; i < a->len; i++) {
        total += a->data[i];
    }

    return total;
}
```

The key difference from the hand-written version is that `a->data` is now
`int *` because we told the macro `TYPE` was `int`. Change the macro call to
`DEFINE_ARRAY(int_array, long)` and the same `reduce_sum` compiles for `long`.
The function above is still hand-written per operation, though — only the
*storage* is generic. That is an important boundary to understand:

> In C, the preprocessor makes **types** generic. It does not make **functions**
> generic. `map` and `filter` will be generated by a macro too, or written once
> per element type.

## Map and filter

`map` transforms every element; `filter` keeps some. Both produce a new array.

```c
struct int_array map_double_all(const struct int_array *a)
{
    struct int_array out;

    int_array_init(&out);
    for (size_t i = 0; i < a->len; i++) {
        int_array_push(&out, a->data[i] * 2);
    }

    return out;
}

struct int_array filter_even(const struct int_array *a)
{
    struct int_array out;

    int_array_init(&out);
    for (size_t i = 0; i < a->len; i++) {
        if (a->data[i] % 2 == 0) {
            int_array_push(&out, a->data[i]);
        }
    }

    return out;
}
```

### Ownership is now on the caller

Returning a `struct int_array` **by value** is fine: it is a small struct
(the data pointer, the length and the capacity). But the pointer inside it
still owns heap memory. The caller must free it:

```c
struct int_array doubled = map_double_all(&a);
/* ... use it ... */
int_array_free(&doubled);
```

This is the C version of Go's slices-and-garbage-collector contract. In Go,
`map` returning a new slice is free; here, every returned collection is a
promise to call `free`. Many real C bugs are a caller who forgot. AddressSanitizer
is your backstop.

## Tests for map and filter

```c
static void test_map(void)
{
    const int values[] = {1, 2, 3};
    struct int_array a = make_ints(values, 3);
    struct int_array doubled = map_double_all(&a);

    CHECK_INT(doubled.len, 3);
    CHECK_INT(doubled.data[0], 2);
    CHECK_INT(doubled.data[1], 4);
    CHECK_INT(doubled.data[2], 6);

    int_array_free(&doubled);
    int_array_free(&a);
}

static void test_filter(void)
{
    const int values[] = {1, 2, 3, 4, 5, 6};
    struct int_array a = make_ints(values, 6);
    struct int_array evens = filter_even(&a);

    CHECK_INT(evens.len, 3);
    CHECK_INT(evens.data[0], 2);
    CHECK_INT(evens.data[1], 4);
    CHECK_INT(evens.data[2], 6);

    int_array_free(&evens);
    int_array_free(&a);
}
```

The `make_ints` helper is itself a small loop, and it is worth having because
every test needs it:

```c
static struct int_array make_ints(const int *values, size_t n)
{
    struct int_array a;

    int_array_init(&a);
    for (size_t i = 0; i < n; i++) {
        int_array_push(&a, values[i]);
    }

    return a;
}
```

## Refactor: taking function pointers

The duplication between `map_double_all` and a future `map_square_all` is
exactly the kind of thing we have been refactoring away all book. The C tool
for "pass the operation in" is a function pointer:

```c
int int_double(int x) { return x * 2; }

struct int_array int_array_map(const struct int_array *a, int (*f)(int))
{
    struct int_array out;

    int_array_init(&out);
    for (size_t i = 0; i < a->len; i++) {
        int_array_push(&out, f(a->data[i]));
    }

    return out;
}
```

Now `map` is generic over the *operation*, and the array macro is generic over
the *element type*. Between them you have most of what Go's generics give you,
without a single template parameter — and with the cost that bind the operation
and the type are still checked at compile time per instantiation.

To generate the whole family for many types, you would put `INT_ARRAY`'s
`map`/`filter`/`reduce` inside a second macro and instantiate it alongside the
array. At that point, it pays to ask whether you are writing a library or a
puzzle; there is a real readability cliff, and it is easy to fall off.

## Wrapping up

What we have covered:

- Using a generated collection (`DEFINE_ARRAY`) as the basis for algorithms
- `reduce`, `map` and `filter` as ordinary loops over the generic array
- Returning a struct by value while still owning the memory inside it
- Passing the operation in as a function pointer to remove duplication
- The boundary: macros generalize types; function pointers generalize
  operations

Go 1.18's slices package gives you `Reduce`, `Map` and `Filter` for free. In C
you now know how to build each, what it costs, and exactly where the compiler
will stop helping and you must take over.
